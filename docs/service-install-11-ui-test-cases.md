# SI11 — поэтапные тест-кейсы реального интерфейса

## Test Scope

SI11 проверяет путь пользователя от Installer-free QA-машин до установки всех
поддерживаемых сервисов **одним планом**, а также реализованные действия на
каждой странице Installer. Этот документ — исполняемый чек-лист, а не отчёт
о проведённых тестах. До начала прогона каждый пункт имеет статус `NOT RUN`.

После отдельного `S11-00` (проверенная целевая очистка QA/Installer без
восстановления ОС) действия acceptance выполняются только в настоящем Windows
Wails `.exe`: мышь,
клавиатура и штатные системные диалоги. Автоматизация может находить
элементы интерфейса и нажимать их, но не вызывать Wails Go bindings, Go,
Ansible, Core или тестовый bridge напрямую, не подменять React handlers и
native dialogs. Журналы и состояние ВМ разрешено читать для сверки, но не
использовать для продвижения сценария. Модульные/регрессионные тесты —
отдельный gate и не подменяют этот UI-прогон.

Перед каждым этапом зафиксировать список реально видимых и доступных
действий текущего билда. Каждому действию назначить кейс ниже; новый
контрол без кейса означает неполное покрытие. Действия, показываемые только
в определённом состоянии, открывать штатным UI-путём. Проверять не все
математически возможные комбинации, а перечисленные переходы состояния,
отрицательные границы и пары факторов; это сохраняет тест выполнимым.

Для каждого кейса записать `PASS / FAIL / BLOCKED / NOT APPLICABLE`, сборку,
экран/контрол, исходное и итоговое состояние, скриншот или запись действия,
видимый безопасный код ошибки. `NOT APPLICABLE` допустим только для
условного контрола, предпосылка которого отсутствует и это доказано.
Все пользовательские подписи, подсказки, ошибки и действия должны быть на
русском языке, кроме общепринятых технических названий и идентификаторов
контракта (например, SSH, TLS, Kafka, `runId`). Это отдельный сквозной кейс
`L01`: его проверяют на каждой открытой странице, форме и модальном окне;
найденную непереведённую строку сразу фиксируют в журнале.
Секреты, содержимое защищённых файлов и пароли не записывать. Для Save,
Verify, Plan и Start дополнительно фиксировать отображённые revision,
plan ID, run ID и terminal result; read-only journal может подтвердить их.

Контрольный указатель по текущим страницам (перед прогоном сверить с
фактической сборкой; новые кнопки добавить в матрицу до PASS):

| Страница | Контролы и кейсы |
| --- | --- |
| App Shell / Проект | Навигация и badge Node `P02/H06`; создать/открыть/закрыть проект `P01–P05`; экспорт и его modal `P06`; общий Save/Verify/Review/refresh `V01–V05`. |
| Серверы | Добавить/изменить/удалить, modal Save/Cancel `H01–H04`; session credentials Save/Clear `H05`; выбор/check/prepare Node `H06–H08`. |
| Топология | Добавить/удалить deployment, размещение/member/host/clear, сервисный и серверный вид `T01–T05`; вкладка «Точки входа», consumer/provider/group и адреса `E01–E04`. |
| Сертификаты | Добавить/изменить/удалить и Cancel для всех четырёх семейств `C01–C02`; Verify и переход из сервиса/обратно `C03–C04`. |
| Сервисы | Список/detail/Топология `S01`; Apply/Reset/Review/Discard `S02–S03`; «Секреты», Cancel, session save, native file chooser `S04`. |
| Установка | Сводка/План/Выполнение/Результат `I01`; build/approve и password controls `I02/I04`; Cancel `I03`; Start/events/result `I04–I05`; защищённые файлы `I06`; repeat `I07`. |

«Логи» сейчас отображаются в навигации как отключённый будущий раздел:
отдельная страница и переход к ней не реализованы. Поэтому в SI11 проверяются
основной ход и результат текущего запуска во вкладках «Установка →
Выполнение/Результат» (`I05`), а не полный исторический поток событий.
Текущий компонент может показывать ограниченный сеансовый список событий;
это не доказательство полноты будущей страницы «Логи». Если раздел станет
доступным в проверяемой сборке, добавить для него отдельный кейс до PASS.

Комбинации, которые обязательно повторить на границах страниц: `нет проекта /
metadata-only / saved managed / draft`, `Node отсутствует / выбран, но не READY
/ READY`, `Verify не запускался / CURRENT / INVALID / STALE`, `план отсутствует
/ свежий / устаревший / одобрен`, `run отсутствует / выполняется / terminal`.
Проверить минимум пары `draft+NOT READY`, `saved+NOT READY`, `STALE+старый
одобренный план`, `READY+смена Node`, `running+переход между вкладками`,
`terminal+reopen`. Не запускать реальную установку ради каждой пары: там, где
достаточно read-only UI состояния, не создавать новый run.

## Environment Requirements

- Список QA Execution Node и target ВМ, инвентаризация и проверенная
  целевая очистка `S11-00`; доказать отсутствие прежнего Installer/runtime и
  QA-сервисов до первого bootstrap. Это не аттестация свежей ОС.
- Текущая Wails-сборка, совместимый immutable bundle, доступные approved
  репозитории/offline artifacts и тестовая инфраструктура для всех десяти
  manifest-пакетов: Keepalived, BIND, DNS client, HAProxy, Kafka,
  PostgreSQL, Redis, Vault, ClickHouse, Docker. Внутренние компоненты вроде
  pg_auto_failover, Sentinel, Keeper и Compose проверяются в рамках своих
  сервисов, а не выдаются за отдельные пакеты каталога.
- Отдельные disposable проекты для CRUD/негативных сценариев и канонический
  проект финальной установки. Действия над disposable проектом не должны
  менять final desired state. Любое тестовое выполнение/Cancel, изменившее
  target, требует повторного подтверждённого `S11-00` перед финальным run.
- Учетные данные и runtime secrets вводятся только штатными UI-полями;
  проверка их отсутствия в portable project может использовать read-only
  аудит после действия, но не прямую запись/правку файлов.
- До каждого WebView-прогона, которому нужен SSH-доступ, подготовить
  незашифрованный PEM private key, совместимый с текущим валидатором
  `internal/runtimesecret`; если такого ключа нет — создать его заранее и
  убедиться, что соответствующий public key уже разрешён на QA-хостах.
  Поддерживаются RSA/EC ключи в PKCS#8, RSA PKCS#1 и EC SEC1 PEM; формат
  `BEGIN OPENSSH PRIVATE KEY` и зашифрованные ключи этим полем не принимаются.
  Сам ключ держать только в `.runtime/secrets/`, не показывать и не выводить.
  Перед запуском проверить срок credential-сессии; после истечения заново
  сохранить credentials через UI и выполнить probe fingerprint, независимое
  сравнение с доверенным источником и явное UI-подтверждение host key.
  Если PEM, его авторизация на QA-хостах или действующая сессия отсутствуют,
  остановить прогон до открытия WebView acceptance-сценария.

## Required Scenarios

### S11-00 — исходная граница

| ID | Действия | Ожидаемый результат |
| --- | --- | --- |
| B01 | Инвентаризировать точные QA ВМ и Installer-owned ресурсы, сохранить безопасные доказательства; выполнить целевую очистку по `service-install-11-cleanup.md`. | Ни один чужой/shared ресурс не удалён; на выбранных узлах нет прежних Installer/QA service runtime, но не заявляется чистая ОС. |
| B02 | Открыть Wails `.exe` и зафиксировать экран без проекта/READY node. | Предыдущие run, installer-runtime и сервисы не «подхвачены» из старого QA; конечный проект не создан вне UI. |

### S11-01 — проект и App Shell

| ID | Действия в интерфейсе, строго по порядку | Ожидаемый результат |
| --- | --- | --- |
| P01 | Нажать «Открыть проект», отменить native folder dialog; повторить и выбрать существующий disposable проект. | Отмена не меняет контекст; открытие показывает именно выбранный проект. |
| P02 | Перейти по всем пунктам навигации и badge Execution Node; закрыть проект, затем снова открыть его через диалог. | Текущий проект очищен при закрытии; повторное открытие показывает сохранённое состояние, badge ведёт к панели узла. |
| P03 | «Создать проект»: выбрать родительскую папку, оставить название пустым, затем задать недопустимое/дублирующееся имя, отменить, открыть снова и задать валидное имя. | Ошибки показаны до записи; отмена ничего не создаёт; валидный проект создан с корректной папкой. |
| P04 | В форме создания изменить название до/после выбора папки, изменить имя папки вручную; создать проект и закрыть/открыть. | Название и путь предсказуемо синхронизируются согласно UI; reopen показывает тот же metadata-only проект. |
| P05 | Проверить «Открыть папку проекта», «Добавить первый сервер»/«Открыть серверы», «Закрыть проект», «Открыть другой проект» в применимых empty/error/saved состояниях. | Каждый переход открывает ожидаемую страницу/диалог; неудачная попытка открыть другой проект закрывает прежний контекст и не показывает его как текущий. Ошибка создания проекта проверяется отдельно в P03 и сохраняет прежний контекст. |
| P06 | На сохранённом проекте открыть «Экспортировать проект»; отменить выбор папки, выбрать destination, «Проверить состав», закрыть без экспорта; повторить, «Экспортировать», «Открыть экспортированный проект», «Готово». | Preview не публикует экспорт; успешный экспорт открывается как отдельный проект; исходный проект не меняется. |

`L01` — на каждом шаге P01–I07 проверять русскоязычность пользовательского
интерфейса; общепринятые технические имена и буквальные коды ошибок допустимы,
смешанные английские фразы в кнопках/подсказках — нет.

Удаление проекта не включено: это был пример возможной цепочки, а не
утверждённая функция; в текущем UI такого действия нет. Достаточная
реализованная цепочка: открыть существующий проект → закрыть → создать новый
→ закрыть → открыть созданный. Никакого удаления файлов для имитации UI
не требуется.

| H08 | Прокрутить длинный список серверов, не теряя нижней панели Execution Node; переключить страницы при NOT READY и READY. | Список скроллится отдельно, панель остаётся доступной; navigation gating соответствует реальному состоянию. |

| V04 | На disposable draft дойти до общего лимита 16 команд и попытаться 17-ю; Discard, reopen. | Лимит и remaining capacity честно показаны, нет скрытого coalescing; canonical проект не повреждён. |
| V05 | В Review проверить «Вернуться к редактированию», «Отменить все изменения», «Сохранить проект» и путь read-only «Обновить проект» при воспроизводимой refresh-error. | Применяется единая транзакция; после committed refresh failure Commit не повторяется, только reopen. |

## Negative Scenarios

- Несовпадающий/dangling server, deployment, endpoint-group и PKI reference:
  безопасная ошибка, без частичного Save и без потери прежних значений.
- Отмена каждого native dialog, modal и confirmation не создаёт проект,
  deployment, credentials, план или run.
- NOT READY/недоступный Execution Node: local Save сохраняется, Verify/Plan/
  Start блокируются корректным prerequisite. Mutation prepare — только после
  явного подтверждения.
- Устаревший project revision, catalog/runtime identity, verification и план:
  ранее одобренный Start не оживает после редактирования.
- Ошибка запуска/потеря связи во время run: тот же runId/status после
  reconnect; нельзя считать spinner или одно событие terminal успехом.
- Конфликт внешних BIND/HAProxy записей и/или старые чужие конфиги не должны
  удаляться «ради теста»; точечное изменение должно соответствовать плану.

## Contract Scenarios

- Portable project содержит только desired fields. Серверы, placement,
  endpoint relation, PKI и supported service settings после Save/reopen
  отображают ровно сохранённые значения; runtime credentials/secret values
  остаются вне него.
- Local Save, target-free Verify, fresh Plan, approval и Start — пять
  отдельных состояний. Переход на следующую стадию без обязательного gate
  запрещён и проверяется видимой UI-реакцией.
- Один full-plan run использует заданные UI placement/secret/PKI/endpoint
  отношения; terminal и per-action результаты читаются из UI, а journal
  только сопоставляется с показанным run ID.
- Повтор того же saved desired state сохраняет identities и даёт реальный
  `changed=0`; не подменять его `changed_when: false` или пропуском сервисов.

## Regression Risks

- CRUD/Discard может оставить невидимый acknowledged draft и позже изменить
  не тот deployment. Межстраничные переходы проверять до и после Save.
- Смена Execution Node/READY может ошибочно привязать старую verification,
  план или session secret к новому узлу.
- Работа с unsupported settings может переписать service config при Save
  другого поля; проверять сохранность после reopen.
- Rehearsal Cancel загрязняет Installer-free baseline; повторить `S11-00` до
  финального однократного запуска.
- Конечный UI-test не доказывает каждую модельную комбинацию placement; для
  неё остаются отдельные regression suites. Но все реализованные кнопки и
  условные действия должны иметь UI-кейс и зафиксированный итог.

## Not Testable Locally / current gaps

- `I03` нельзя проводить на том же baseline непосредственно перед
  непрерывным финальным run. Без изолированной rehearsal ВМ или повторного
  проверенного reset этот кейс `BLOCKED`, а не пропущен с `PASS`.
- Действия, для которых текущий билд не показывает условный контрол,
  фиксируются с причиной и снимком состояния; недоступный реальный Wails
  bridge не заменяется mock/direct backend harness.
