# UI-01 — редактор Ansible-проекта

Статус: PLAN / IN PROGRESS. Дата: 2026-09-05.
UI-01A–UI-01E3 DONE; UI-01D принят владельцем без финального review;
следующий отдельно авторизуемый этап — UI-01E4. UI-01B реализует только read-only desktop
surface. План не является разрешением на автоматический старт всех milestones.
Каждый этап запускается отдельным запросом владельца.

## Цель и границы

Рабочее desktop-приложение: создать чистый проект, добавить серверы и сервисы,
задать размещение, проверить изменения через Core и сохранить обычные
Ansible-файлы. Повторное открытие показывает сохранённую конфигурацию.

Основа: [макет](ui-design-01-mockups.html),
[сценарий создания](ui-project-creation-design.md),
[UI-BE-03 writer](ui-be-03.md), [границы backend](backend-and-ui.md),
[portable contract](project-contract.md).

В UI-01 входят:

- Wails/React оболочка, типизированный транспорт к существующему Go backend;
- Проект, Серверы, Топология, Сертификаты, Сервисы и общий review/save;
- настройка PKI-профилей и ссылок сервисов на них, без runtime-выпуска;
- создание metadata-only проекта, безопасное первое сохранение;
- общий сеансовый ввод credentials для всех серверов;
- отображение validation findings и происхождения значений;
- открытие существующего проекта и экспорт сохранённой полной конфигурации.

Не входят: UI запуска apply/verify, approval execution plan, подготовка Execution
Node, отмена выполнения, история запусков, подписка на task events и PKI
materialization. Это UI-02 поверх уже готовых UI-BE-04/EXEC-OBS-01.
Макет Установки: Сводка → План → Выполнение → Результат. Подготовка
Execution Node выполняется на странице Серверы и не является частью
Installation.
План показывает действия, зависимости и targets из Core отдельно от Execution
Node. Результат сопоставляет действия плана с наблюдаемыми исходами конкретного
runId, включая verify, ошибки и пропуски. Просмотр не запускает повторный verify.
Эти вкладки проектируются сейчас, но реализуются в UI-02, не UI-01.
Импорт шаблонов со слотами и перепривязкой серверов предлагается вынести в
отдельный follow-up; обычное открытие native project обязательно в UI-01.

## Инварианты

1. Desired state — только portable Ansible project. React не парсит YAML,
   не вычисляет topology, precedence, service defaults, endpoints или PKI.
2. Go владеет прикладной сессией, транзакциями и review. Core — инфраструктурной
   интерпретацией и обязательным staged proof.
3. Новый проект содержит только согласованные metadata; inventory, host_vars,
   group_vars, неявных серверов и deployments при создании нет.
4. Недозаполненная форма — несохранённый ввод сессии, не второй desired-state
   store. Отсутствие валидного промежуточного состояния не разрешает commit
   BLOCKED-плана; допустимые связанные изменения собираются в bounded session.
5. Core/Python выполняются на выбранном Execution Node, не на Windows Installer.
   Создание metadata может быть локальным; authoritative save требует Core.
6. Сохранение файлов не запускает установку. Target-free validation не означает
   отсутствие SSH к Execution Node, но исключает контакт с целевыми hosts.
7. Сервисы имеют отдельный пункт меню. Вход из Топологии открывает тот же
   редактор выбранного deployment; возврат сохраняет выбор и введённые данные.
8. Одна техническая учётная запись и пароль/ключ текущего сеанса применяются ко
   всем серверам. Значения не попадают в проект, review, логи или ответы query.

## Обязательная сверка перед каждым milestone

Перед каждым ML, включая backend-этапы и финальную приёмку:

1. Прочитать актуальные AGENTS.md, CURRENT_STATE.md, этот план и
   [макет](ui-design-01-mockups.html) с [описанием UX](ui-design-01.md).
2. Пройти относящийся к этапу сценарий макета; сопоставить навигацию, формы,
   переходы, empty/error/unsaved состояния с задачами и контрактами этапа.
3. Зафиксировать результат сверки в стартовом отчёте: экраны/сценарии, найденные
   расхождения и принятые решения. Для backend ML указать обслуживаемый UX.
4. Противоречия макета, плана и Core не разрешать молча в коде: сначала
   согласовать существенные изменения и синхронизировать документы/макет.
   Демонстрационные данные и PASS не являются инфраструктурным контрактом.
5. При приёмке повторить сверку и явно перечислить согласованные отклонения.

Порядок интерфейса: Проект → Серверы → Топология → Сертификаты → Сервисы →
Установка → История. Это рекомендация, не жёсткий wizard: можно вернуться
к любому разделу. Для сервисов без TLS этап настройки сертификатов необязателен.
Топология создаёт deployment/type/mode/members и размещение; Сертификаты задают
PKI intent; Сервисы редактируют параметры тех же экземпляров и ссылки на профиль.

## UI-01A — контрактный preflight

Detailed execution plan: [UI-01A contract preflight](ui-01a.md).
Accepted result: [contract freeze](ui-01a-contract-freeze.md),
[toolchain](ui-01a-toolchain.md), [review](ui-01a-review.md) and
[documentation QA](ui-01a-qa.md). Status: **DONE**; blocking findings: **0**.

Работы:

- составить таблицу экран → существующий Go method/contract → отсутствующая
  возможность; различить реализованный backend и ранее описанные интерфейсы;
- зафиксировать create/open metadata envelope и способ распознавания намеренно
  пустого проекта, не маскирующий повреждённый существующий проект;
- определить ownership нового inventory и первый staged snapshot: текущий
  writer не даёт права изменять произвольный inventory/hosts.yml;
- определить bounded first-write transaction, форму review, transient draft
  lifecycle и поддержку неполного ввода без ослабления Core;
- зафиксировать минимальный способ выбрать существующий READY Execution Node
  для editor validation без реализации его bootstrap UI;
- выбрать и зафиксировать Wails/frontend toolchain и native build prerequisites;
  использовать существующие DTO, не создавать универсальный shell/SSH bridge;
- сверить roadmap с фактическим каталогом. Упоминание Patroni не считать
  разрешением реализовать новую production-службу: PostgreSQL baseline сейчас
  include-based PostgreSQL/pg_auto_failover. Согласовать точные fixtures;
- утвердить границу полного экспорта и отложенного template import.
- проверить наличие typed PKI edit/query contracts и ownership PKI inputs;
  недостающие возможности включить явно в G, без второго DTO и store.

Приёмка: для каждого gap указаны контракт, владелец слоя, этап реализации и
негативные тесты. Не осталось неявного bypass для initial/staged validation.
Core-contract и safety review — 0 blocking findings. Код продукта не меняется.

## UI-01B — desktop shell и read-only интеграция

Статус: **DONE**. Evidence: [UI-01B](ui-01b.md) and
[review](ui-01b-review.md); blocking findings: **0**.

Работы: Wails shell, React навигация, компоненты форм/таблиц/findings, постоянные
название/путь проекта и edit-state; native выбор папки; read-only opening через
existing snapshot boundary; минимальная привязка к уже READY Execution Node.
Существующие неподдерживаемые файлы открываются с понятной read-only причиной.
Установка/История пока явно обозначены как будущие разделы, без fake PASS.

Приёмка: запускается собранное native-приложение на Windows; реальный snapshot
получен через RED OS Execution Node. Нет записи project bytes, target contact,
локального Python или потери контекста при навигации. Node unavailable, timeout,
несовместимость и неизвестная версия контракта отображаются безопасно.
Минимум 1024×720, управление клавиатурой, focus и loading/empty/error состояния.

## UI-01C — создание metadata-only проекта

Статус: DONE. Реализация и acceptance evidence: [docs/ui-01c.md](ui-01c.md).

Работы: CreateProject в Go и UI; уникальная identity, name/path, atomic publication
новой папки; recent-project metadata; cancel/open/reopen пустого проекта.
Не создавать деревья inventory/variables или примеры конфигурации.

Приёмка: создание работает без Execution Node; disk assertions подтверждают
точный минимальный состав. После restart пустой проект распознаётся корректно.
Existing destination, path escape, symlink/reparse point, race, отказ доступа,
частичная ошибка и cancel не повреждают существующие файлы и не дают ложного
успеха. Отсутствующий inventory старого проекта не объявляется новым проектом.

## UI-01D — first-write и общая edit/review session

Статус: **DONE (OWNER ACCEPTED WITHOUT REVIEW)**. Реализация и acceptance
evidence: [docs/ui-01d.md](ui-01d.md). Финальный revision-bound review принят
владельцем без запуска; commit создан после executable gates.

Работы: реализовать только согласованные A расширения inventory ownership и
first-write; backend-owned transient session с baseRevision, bounded intents,
review/discard/commit; общий UI review и индикатор несохранённых изменений.
Инфраструктурные настройки остаются Core-owned; не копировать правила в Go.
Производные bootstrap inputs не сохраняются раньше одобренной транзакции.

Review требует текущий READY Execution Node, но UI-01D не реализует его полный
выбор, bootstrap или preparation UI. Session и draft сохраняются в памяти при
временной недоступности узла; Review/Save блокируются до восстановления
текущего authoritative Core proof. Execution Node selection/readiness является
application context, а не project desired state. Полная панель узла и её
selection/preparation lifecycle принадлежат UI-01E; Installation только
потребляет READY node и current saved/Core-valid revision.

Приёмка: реальный Core на RED OS доказывает первый полный staged candidate и
последующее изменение. До commit canonical bytes неизменны; после commit
созданы только необходимые native files. Проверить missing Node, BLOCKED,
shadowed edit, stale revision, expired plan, duplicate commit, disk failure и
crash recovery. Повтор без изменений — NO_CHANGE. Чужой inventory не переписан.
UI navigation сохраняет ввод; project switch/close требует явного discard или
возврата к редактированию. Незавершённый ввод не экспортируется и не исполняется.

На этом этапе используется небольшой контрактный fixture/тестовый клиент;
полные формы появляются в E–H, не дублируются в D.

## UI-01E — серверы и общая сеансовая identity

UI-01E выполняется через отдельно авторизуемые E1–E6. UI-01E1 DONE:
`ui-01e1-architecture.md` фиксирует v1alpha4 server CRUD integration,
Core-проекцию desired hostname/SSH port и generic delete-reference contract.
UI-01E2 и UI-01E3 DONE. Следующий отдельно авторизуемый этап — UI-01E4.

Работы: add/edit/remove server, identity и transport fields через D; единый ввод
технического пользователя и credentials сеанса. Никаких per-host credential
форм. Runtime secret broker отвечает за secret lifetime; UI получает только
availability, не сохранённое значение. Connection check — отдельное явное
read-only действие, если поддержано/согласовано в A; не условие ввода адреса.

E5 не потребляет target credential из E3 и не использует его как prerequisite
для navigation gating или READY Execution Node. E5 проверяет и подготавливает
только Execution Node через его отдельную trusted application binding. E3
target lease остаётся локальным и неиспользуемым до реализации фиксированного
UI-02 transport; до этого target connection/elevation/preparation не запускаются.
Внутренний broker reference не возвращается через Wails/React status.

Приёмка: несколько серверов используют одну session identity; никакого secret
в snapshot, diff, events, audit или проекте. Неизвестный/изменённый SSH host key
не принимается автоматически. Проверить duplicate identity, invalid transport,
удаление используемого host и несохранённую форму. Факты имеют timestamp и
отделены от desired fields. Редактирование само не подключается к target.

## UI-01F — каталог экземпляров, топология и связи

Работы: выбор type/mode из каталога, создание независимых deployments;
виды по сервисам/по серверам, members/roles/placement, endpoint groups,
deployment assignment и поддержанные зависимости. FQDN/VIP/PKI preview —
read-only Core projections; неподдержанный редактор честно read-only.
Контекст перехода в общий service editor сохраняется; до H действие явно
недоступно, после H открывает тот же deployment с возвратом в Топологию.

Приёмка: связанный batch серверы+сервис+размещение проходит review/Core/commit;
переходы не теряют draft и selection. Проверить неназначенный host, constraints
ролей/размещения, dangling references, конфликт endpoints и удаление зависимого
объекта. Ни frontend, ни Go не выводят самостоятельно новые infra defaults.
Тестировать штатные шаблоны и несколько независимых кластеров из каталога.

## UI-01G — Сертификаты: редактор PKI-профилей

Работы: отдельная страница после Топологии и перед Сервисами; список и
создание/редактирование PKI-профилей через typed backend. Scope, CA reference,
допустимые usages и другие поля — из существующего PKI contract. Потребители,
SAN и effective preview вычисляются Core, не frontend. Недостающие PKI writer
операции реализовать только по gap list A с existing staged proof и ownership.

Приёмка: профиль доступен для выбора в H, ссылки не дублируют профиль; изменение
scope/usage и удаление используемого профиля проходят review/Core checks.
Проверить неизвестную CA, неверный scope/usage, dangling references и изменение
SAN после перестановки members. Private keys/passwords не видны и не сохраняются
в проект. CERTIFICATE_REISSUE_REQUIRED не обходится: UI показывает blocker.
Нет выпуска, ротации, копирования сертификатов на hosts или apply/verify.
Для сервиса без TLS профиль не создаётся принудительно.

## UI-01H — настройки сервисов и ссылки на PKI

Работы: отдельная страница Сервисы для созданных в Топологии экземпляров;
schema-driven fields, origins, default/override/reset, protected/unsupported
fields и Core findings. Выбор существующего PKI-профиля из G, переход в
Сертификаты и обратно без потери draft. Вход из Топологии открывает тот же
редактор. Не создавать второй deployment или независимую конфигурацию.

Приёмка: несколько экземпляров одного type независимы, отсутствие любого
сервиса допустимо. Режимы определены каталогом, не React. Проверить invalid,
unknown/reserved setting, конфликт scope, secret-like input, смену режима и
удаление связанного deployment. Неполная конфигурация остаётся в общей сессии;
guards не ослабляются ради отдельной кнопки сохранения. Проверить отсутствующий,
несовместимый и удалённый PKI-профиль, обновление ссылок и сценарий без TLS.
Использовать fixtures из A.

## UI-01I — portable export и reopening

Работы: экспорт только сохранённой полной конфигурации в согласованный A формат;
preview включаемых документов, совместимость и безопасный выбор назначения.
Повторное открытие экспортированного native проекта. Не реализовывать template
slots, произвольный archive import или adoption чужих файлов в этом этапе.

Приёмка: export/reopen сохраняет canonical semantics по Core snapshot, включая
поддержанные extension fields. Draft, credentials, generated state, workspaces,
логи и результаты исключены. Для неизвестных/потенциально секретных файлов —
явное блокирование или согласованный allow-list, не слепое копирование папки.
Проверить overwrite/conflict, escape/symlink, несовместимость и частичную ошибку.
Экспорт проходит standalone target-free validation на RED OS без UI/Go.

## UI-01J — итоговая приёмка

Обязательный сквозной путь в собранном desktop-приложении:
create → servers → topology → certificates (если нужны) → service settings →
review → Core proof → commit →
close/reopen → export → standalone validation.

Матрица: пустой и существующий проект; supported writable и human read-only;
несколько deployments; неполные формы; изменение файлов внешним редактором;
cancel/discard; restart; Node unavailable; secret redaction; keyboard navigation,
модальные focus traps, 1024×720 и широкое окно, светлая/тёмная темы.

Final gates:

- frontend typecheck, lint, unit/component tests, production build и native smoke;
- Windows GUI E2E + текущий working tree Core на RED OS, без target mutations;
- affected Go tests; `go test ./...`, `go vet ./...`; RED OS race affected packages;
- Core full suite и affected service suites; relevant UI-BE-02/03/04 и EXEC-01A
  regressions в пределах затронутых boundaries;
- catalog/schema reproducibility, secret audit, `git diff --check`;
- core-contract-reviewer и safety-reviewer должны вернуть 0 blocking findings до DONE;
- зафиксировать команды, durations/counts, реальные fixtures и ограничения;
  удалить только собственные QA artifacts, сохранить unrelated изменения;
- обновить CURRENT_STATE/roadmap, focused final commit и проверка worktree.

Full remote Kafka apply cycles не входят в UI-01 по умолчанию: приёмка редактора
не должна менять общий QA deployment. Если найден дефект execution wiring,
выделить scope и согласовать изолированную проверку до контакта с targets.

## QA по этапам и условия DONE

До J каждый milestone запускает только affected frontend/backend/contract tests
и свои обязательные негативные сценарии. Изменения Core/Ansible проверяются
на RED OS, но не на Windows. Component mocks проверяют UI states, не заменяют
реальный first-write proof в D и native acceptance в J. Недоступная VM — явный
QA blocker для remote proof, не PASS по мокам.

UI-01 DONE только после J. A–I не дают права объявить весь редактор готовым.
UI-02 не стартует автоматически после завершения UI-01.
