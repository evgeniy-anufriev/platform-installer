# V1 reference audit

## Purpose

V1 is reviewed as executable requirements and accumulated operational knowledge. This audit does not declare V1 code reusable without review.

## Strong foundations to preserve

- `ServiceDefinition` is distinct from project service instances.
- Multiple instances/deployments of one service type are conceptually supported.
- Desired hosts and discovered `HostFacts` are separate.
- Endpoint groups/bindings and TLS preview are represented as project concerns.
- Roles are intended to consume ordinary Ansible variables.
- Execution node and target hosts are distinct.
- Package acquisition follows `INSTALLED -> REPOSITORY -> PAYLOAD -> BLOCKED`.
- Runtime secrets, host-key trust, cancellation, journals and redaction have concrete requirements and regression tests.

## Structural problems V2 must not inherit

- service catalog and topology rules are primarily Go-owned;
- desired project exists through domain, blueprint, persistence and frontend representations;
- inventory/group variables are generated by Installer-specific Go code;
- several plan/execution models represent overlapping workflows;
- endpoint binding lacks an explicit listener identity in parts of V1;
- topology members do not consistently have stable member identity and multiple roles;
- general and special-service TLS concerns are partly implicit;
- frontend project models and major pages are very large;
- Wails API surface follows many page actions rather than a small stable protocol;
- standalone payload does not yet own validation, topology compilation and plan contracts;
- Kafka role is a contract example rather than a complete production deployment.

## Behavioral assets to port as fixtures/tests

- no service selected means no hidden default instance;
- standalone PostgreSQL, Patroni and two independent pg_auto_failover deployments;
- Kafka KRaft role allocation and quorum constraints;
- multiple endpoint domains, aliases, wildcard and VIP SAN behavior;
- certificate aggregation by explicit scope rather than service instance;
- Docker/Podman absence and passworded sudo as known facts, not discovery failure;
- explicit `ACTION_REQUIRED` versus `BLOCKED` readiness semantics;
- stale-plan rejection and fingerprint checks;
- unknown/changed SSH host-key handling;
- cancellation, retry, interrupted runs and partial host results;
- offline payload verification and no Internet fallback;
- canary-secret scans across events, results and diagnostics;
- idempotent second execution.

## Reuse classification

### Reuse after focused review

- generic role task patterns and distribution mappings;
- target-preparation, Java, OpenSSL and certificate materialization techniques;
- callback redaction techniques;
- artifact manifest parsing concepts;
- selected SSH/session cancellation utilities;
- test fixtures that do not depend on V1 schemas.

### Rewrite behind V2 contracts

- topology validator/compiler;
- service catalog loader;
- inventory projection;
- deployment plan and result generation;
- project persistence and import/export;
- execution orchestration;
- frontend API, state and editors.

### Do not carry forward

- Go domain objects as Ansible role input;
- duplicated frontend service catalogs;
- SQLite as a second portable desired-state format;
- generated workspace as editable authority;
- task display names as event identity;
- milestone-specific playbook names as backend API;
- demo/default service deployments.
