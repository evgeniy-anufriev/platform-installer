## Цель и граница

Пользователь существующего управляемого проекта получает новый immutable
runtime bundle для изолированного контура и в окне «Проект» выбирает
«Обновить набор установки». Пользователь кладёт полученный каталог bundle
в `bundle/` внутри проекта. Приложение автоматически обнаруживает
только эту точную подпапку, проверяет её содержимое и после явного нажатия
«Привязать» публикует пакет в свой локальный
immutable кэш и перепривязывает проект. Пользователю не нужны Go, CLI или
ручное редактирование YAML. Это решение владельца заменяет ранее намеченный
QA-only сценарий с заранее опубликованным bundle.

Путь поставщика: разработчик в доверенной среде подготовки вызывает существующую
CLI-команду `ansible-core/tools/build_execution_runtime_bundle.py` с явными
`--runtime-input`, `--output`, `--bundle-version` и `--core-version`, затем
проверяет результат через `platform-installer -command validate-bundle -bundle
<output>`. Собранный каталог передаётся заказчику целиком через разрешённый
канал. Команда не требует UI и не запускается на чистом целевом сервере;
она использует уже существующий сборщик, не вводя второй формат bundle.

Путь пользователя: поставщик передаёт пакет → пользователь переносит его в
защищённый контур → перезапускает Installer → открывает существующий проект →
открывает проект → видит найденный проверенный пакет с версиями/digest →
нажимает «Привязать» → приложение публикует и перепривязывает →
пользователь при необходимости заново готовит Execution Node и строит план.

Bundle поставляется отдельно через разрешённый канал. В этой функции нет
интернет-скачивания, сборки, выбора `latest`, обновления самого desktop
приложения или нового формата пакета. `<project>/bundle/` — только временный
источник импорта: она не входит в каноническую ревизию проекта и штатный
экспорт, не изменяет `project.yml` при обнаружении и не является постоянным
местом хранения после публикации. Исправление кода desktop-приложения
требует доставки новой версии приложения; runtime bundle обновляет только
вложенный Core/Ansible/сервисный runtime. Выбранная пользователем папка —
источник импорта, но не постоянная authority: после публикации используется
только повторно проверенная immutable копия в локальном кэше.

По решению владельца локальный кэш приложения называется `cache/<digest>/`,
а источник поставщика — `<project>/bundle/`. Старый кэш приложения
`<repo>/bundle/<digest>/` остаётся только совместимым read-only источником,
если в новом `cache/` ещё нет проверенного набора. Переименование не удаляет
старые файлы и не меняет формат самого bundle.

## Контракт действия

1. Read-only предварительный просмотр берёт путь только как
   `<открытый project root>/bundle` в Go, вызывает существующий
   `executionbundle.ValidateRoot`,
   показывает текущие `artifactLock.digest`/`catalogLock.digest`, digest
   найденного bundle/каталога и ревизию проекта. Путь не проходит через
   React DTO. UI показывает проверенные версии и digest для подтверждения
   пользователем. Проверка целостности bundle не доказывает его происхождение:
   поставка и перенос в защищённый контур остаются доверенным операторским
   каналом в текущей модели, цифровая подпись здесь не вводится.
   Ещё до обнаружения нового пакета при открытии проекта приложение сравнивает
   сохранённую пару lock с доступным проверенным локальным bundle. Если пары
   не совпадают или подходящего bundle нет, на странице «Проект» явно
   показывается «Нужна перепривязка набора установки» и безопасное объяснение;
   прямые сохранённые сведения проекта остаются видимыми, но каталожно-зависимое
   редактирование/планирование остаётся заблокированным. Никакой автоматической
   записи при открытии нет.
2. Действие допускается только для открытого управляемого проекта без
   несохранённого черновика и без незавершённого Start/активного выполнения.
   По решению владельца доступность Execution Node не является обязательной
   для перепривязки: прежний bundle может быть уже недоступен, и удалённая
   проверка с его runtime тогда невозможна. Вместо неё Installer использует
   локальную операционную запись последнего Start для пары «канонический путь
   проекта + стабильный project ID» в своём защищённом каталоге данных, не в
   `project.yml` и не в event mirror. Отсутствие записи означает только, что
   **этот экземпляр Installer** не зафиксировал Start; оно не доказывает
   отсутствие выполнения, начатого с другого рабочего места. Это принятая
   владельцем граница доверия локальной схемы. Повреждённая или недоступная
   запись блокирует обновление, а не трактуется как «нет запуска».
   Перед отправкой Start локальная запись атомарно и устойчиво переходит в
   `PENDING` с идентичностью проекта/ревизией/планом **и исходного Execution
   Node**: сохранённые ID, адрес, SSH-порт и подтверждённый host-key
   fingerprint. Смена выбранного узла, отсутствие любого поля или несовпадение
   этой идентичности запрещает recovery. После успешного ответа
   атомарно фиксирует тот же `runId`; терминальное состояние записывается
   только после авторитетного GetExecution/результата. При перезапуске
   нетерминальная запись без `runId` остаётся `UNKNOWN` и блокирует
   перепривязку. Время ожидания/TTL не превращают её в terminal.
   Владелец разрешил отдельное аварийное UI-действие «Снять блокировку запуска»
   только для найденного по локальной записи `runId`, который не принадлежит
   текущему сеансу Start. При обычном выполнении кнопка скрыта. Для такого
   осиротевшего `runId` Installer через подтверждённые SSH-учётные данные
   и проверенный host key запрашивает именно этот run на **том же исходном**
   Execution Node. Ответ должен содержать тот же `projectIdentity`, что и
   локальная запись; отсутствие или несовпадение блокирует кнопку и отмену.
   Если run активен — Installer вызывает существующий CancelExecution и
   ожидает авторитетного терминального результата, не удаляя журнал, результат
   или файлы run. Результат Cancel также сверяется по projectIdentity; если
   поле отсутствует, Installer повторяет GetExecution, и до доказанного
   terminal локальную блокировку не снимает. Подключение к Execution Node
   разделяется на две границы: (a) транспортная доверенная SSH-привязка,
   доступная независимо от bundle проекта после обычной проверки ключа,
   учётных данных и host-key approval, и (b) runtime-привязка, которая
   по-прежнему требует совпадающий проверенный bundle для Core Verify,
   подготовки, плана и Start. Аварийный GetExecution/CancelExecution
   получает только исходный runId через транспортную привязку; она не
   превращается в общую runtime-привязку, не выдаёт release evidence и не
   допускает обхода обычных операций. Проверка соединения/узла может работать
   через транспортную привязку при несовпадающем bundle; подготовка и работа
   с проектом сохраняют прежние runtime-гейты. Кнопка доступна только после
   авторитетного обнаружения именно этого run на узле. Если узел недоступен,
   run не найден, статус неизвестен или локальная запись содержит `PENDING`
   без `runId`, кнопка скрыта и блокировка остаётся. Ручного удаления только
   локальной блокировки без найденного run нет. Окно между отправкой Start и
   получением `runId` остаётся отдельным recovery gap: его нельзя закрывать
   TTL или предположением, что запуск не состоялся.
   `StartApprovedInstallation` ставит под `App.editMu` резервирование
   `startInFlight` до отпускания mutex перед удалённым вызовом и снимает его
   на всех путях возврата; подтверждение обновления проверяет тот же флаг под
   тем же mutex. Во время проверки, публикации и CAS обновление удерживает
   отдельное состояние `runtimeUpdateInFlight`, которое Start проверяет до
   резервирования. Известный run допускает обновление только после
   подтверждённого терминального состояния через существующую модель run;
   недоступный/неизвестный статус не трактуется как terminal. Старый
   одобренный план после обновления недействителен. Само чтение offer ничего
   не меняет.
3. На подтверждение React возвращает только непрозрачный одноразовый
   идентификатор предпросмотра. Go держит
   найденный источник и ожидаемую project revision в короткоживущем сеансе,
   повторно проверяет источник и digest перед публикацией. Ни root проекта,
   ни root bundle из React не принимаются. Истёкший или чужой предпросмотр
   отклоняется; после смены проекта/черновика он недействителен.
4. Приложение вызывает существующий `executionbundle.Cache.Publish`:
   копирование в staging, повторная проверка содержимого, атомарная
   публикация в активный кэш. Перед публикацией Go повторно валидирует
   выбранный источник и сравнивает его bundle/catalog digest с подтверждённым
   preview. После `Publish` Go обязательно сравнивает digest и catalogDigest
   **возвращённой проверенной копии** с тем же preview до вызова
   `UpdateRuntimeLockSet`. Если источник подменился во время копирования и
   опубликована иная копия, проект не перепривязывается; UI показывает
   отдельное состояние «Пакет опубликован, привязка не выполнена».
   Если публикация прошла, но запись проекта
   прервана, при новом открытии проект остаётся со старыми lock и
   read-only `CATALOG_UNAVAILABLE`; пользователь может повторно выбрать тот
   же пакет или продолжить с уже проверенной копией в кэше. Нельзя выдавать
   частично выполненную цепочку за завершённое обновление проекта.
   Сразу после `Publish`, ещё под `App.editMu` и до чтения/повторного открытия
   проекта, App заменяет `availableBundleRoot` и источник
   `projectlifecycle.Service` на root опубликованной копии и инвалидирует
   старый Execution Node binding, который удерживал startup bundle/release.
   Даже если последующий CAS не прошёл, App не обращается к уже удалённому
   cache root: он показывает прежние project locks и новый кандидат для
   безопасного повтора. После restart обычный startup resolver видит ровно
   опубликованный bundle, а проект со старым lock открывается read-only.
   Если `Publish` возвращает ошибку после публикации/очистки, App повторно
   проверяет именно прежний runtime root. Если он исчез или перестал
   проходить проверку, App немедленно сбрасывает эту привязку и каталог в
   текущей сессии независимо от digest фактически опубликованного пакета;
   CAS проекта не вызывается. Прежний lock на диске сохраняется.
5. Для неизменного и изменившегося каталога используется существующая узкая
   `installer.Backend.UpdateRuntimeLockSet`: она проверяет полный project
   revision CAS, прежнюю пару lock, фактический digest immutable bundle и
   закрытый каталог, затем атомарно обновляет только `artifactLock` и
   `catalogLock` в `project.yml`. Обычный ProjectWriter по-прежнему не может
   менять эти поля. Если digest кандидата равен текущему, показывается
   «Обновление не требуется» без записи и без перепубликации.
6. После commit приложение повторно открывает проект, проверяет новую пару,
   сбрасывает производные Verify/план/подтверждение, динамическую привязку
   Execution Node и сеансовые секреты. Пользователь заново готовит узел при
   необходимости, выполняет Core Verify и строит свежий план перед Start.
7. Ошибка до commit проекта означает, что его lock не изменён, но новый
   bundle уже может быть опубликован; UI различает эти два результата.
   Ошибка при обновлении
   представления после commit не называется «откатом»: приложение сверяет
   lock с диска и показывает отдельное состояние «Привязка записана, обновите
   проект»; повторное подтверждение без свежего offer запрещено.

## UX

На странице «Проект» — ранний статус совместимости уже при открытии, кнопка
обнаружения офлайн-bundle в `<project>/bundle/`, read-only карточка
текущей и выбранной пары digest и версий, объяснение, что сохранённые
сервисы/серверы/секретные ссылки не
заменяются. Перед публикацией и commit — подтверждение с последствиями:
старая проверка и план станут недействительными; настройки сервиса могут
потребовать повторной Core-проверки; узел выполнения может потребовать
подготовки. Кнопка недоступна, если кандидат не проверен, черновик или run
активен. Никаких raw YAML, секретов или
ручного ввода project lock; путь к кандидату не попадает в React. Справка
описывает эту реальную кнопку после её реализации, не DEV/QA CLI.

## Проверки

- Подпапка отсутствует: no-op, никаких записей. Неверный/подменённый/изменившийся источник,
  symlink/reparse, недостающий компонент:
  fail closed до публикации/изменения проекта.
- Открытие проекта со старой парой lock показывает раннее понятное требование
  перепривязки без обращения к Core/Execution Node и без изменения проекта;
  при совпадающей паре предупреждения нет.
- Совпадающая пара: no-op, ноль записей.
- Новый bundle с тем же каталогом и с новым каталогом: успешная CAS-замена,
  повторное открытие и только lock-изменения в `project.yml` после
  проверенной immutable публикации.
- Несовпавшая ревизия/старый digest, изменившийся кандидат, повреждённый
  bundle: отказ без изменения проекта; отдельно указать, успела ли пройти
  публикация.
- Активный черновик, pending Start или нетерминальный/неизвестный run:
  действие недоступно и backend отказывает. Гонка Start↔Publish проверяется
  управляемыми барьерами до и после отпускания `editMu` в Start.
- SSH/host-key connection и безопасная проверка узла работают при старом или
  отсутствующем project bundle; Core Verify, Prepare, Plan и Start остаются
  заблокированными без подходящей runtime-привязки. Аварийный доступ ограничен
  сохранённым runId, исходным узлом и исходным projectIdentity. Смена узла,
  другой projectIdentity или отсутствие identity в ответе блокируют Cancel и
  локальное снятие блокировки. При текущем run и `PENDING` без runId аварийная
  кнопка не показывается.
- После публикации App использует новый источник в той же сессии; после
  перезапуска и после post-publication/pre-CAS отказа не обращается к
  удалённому старому cache root.
- Подмена источника между preview, pre-publish validation и копированием:
  несовпавший digest опубликованной копии блокирует CAS и не выдаёт SUCCESS.
- Сбой после атомарного commit: отдельный статус с дисковой сверкой, без
  ложного сообщения об откате и без повторного commit.
- Сбой после публикации, но до project commit: старый lock сохранён,
  опубликованный bundle можно безопасно выбрать повторно; после restart
  нет ложного SUCCESS, нет выбора `latest`.
- Старый approved plan/Verify/сеансовые секреты и Execution Node binding не
  переживают успешное обновление.
- React/Wails реальное действие через UI на одноразовой копии проекта; после
  обновления Core Verify и новый план. Не запускать общий SI11 план этим тестом.
- Go focused/full/vet, frontend tests/lint/build, Wails build, `git diff --check`.

## Не входит

Новый публичный контракт, миграция всех проектов, автопоиск newest,
изменение обычного Save/ProjectWriter, интернет-загрузка или сборка bundle
из UI, автоподготовка Execution Node, ослабление runtime digest при Start.
