# NET-03.1: DNS Client / Split DNS Runtime Adapters

Document scope: the original milestone contract/design. Historical status, review
and QA checkpoints are collected separately; current status and authorization
are recorded only in [CURRENT_STATE](../../../CURRENT_STATE.md).

NET-03.1 provides `services/dns-client`, a separate host-scoped service package
that configures split DNS clients for a referenced authoritative BIND
deployment.  It does not extend the BIND role, create logical member IDs, use
roles, or persist generated state.

The only initial managed setting is `configuration.dnsServerRef`.  It must
reference a valid BIND deployment with exactly one primary, one-or-more
secondaries, canonical IPv4 addresses and a managed authoritative zone.  The
existing Core DNS projection derives the primary-first, deterministic server
list and the managed route domain.  DNS addresses and the zone are never
duplicated in client configuration.

DNS client Verify checks a managed project host through the normal system
resolver. Endpoint records are published by the source service's DNS hook and
may not exist when DNS client Verify runs. Their publication and resolution
belong to the source service's later verification, not this adapter.

Placement is inventory-owned.  A participating host declares only an empty
deployment entry, for example `platform_deployments.dns-clients: {}`.  An
optional `networkManagerConnection` is a future host-specific runtime adapter
override; no roles or logical members are introduced.

## Runtime adapters

If `systemd-resolved.service` exists, it is selected even when NetworkManager
also exists.  The role owns only
`/etc/systemd/resolved.conf.d/platform-installer.conf`, with a deterministic
`DNS=` list and `Domains=~<managed-zone>`.  The route-only domain preserves
split DNS: managed names route to authoritative BIND, while unrelated names
continue through the existing default resolver path.  The role never sets
`FallbackDNS`.

Before using the resolved adapter the role accepts only known resolved-owned
`/etc/resolv.conf` symlinks.  A regular file or unexpected link blocks with
`DNS_CLIENT_RESOLV_CONF_CONFLICT`; the role never replaces or owns that path.

When resolved is absent, NetworkManager is selected.  It modifies an active
persistent profile only after proving a `dnsmasq` split-DNS backend.  The
connection is an explicit validated override or the unique active IPv4
default-route connection.  Ambiguity blocks, and an unsupported split-DNS
backend blocks with `DNS_CLIENT_SPLIT_DNS_UNSUPPORTED` rather than degrading
to global authoritative DNS.  The adapter uses `nmcli device reapply`; it does
not bring a connection down/up.

## Acceptance

See [historical checkpoint](evidence/documentation-additional-checkpoints-20261012.md#net-03-1-checkpoint-001). Current status: [CURRENT_STATE](../../../CURRENT_STATE.md).

The NetworkManager fallback has focused contract coverage.  Runtime QA for it
is deliberately deferred until a host without a `systemd-resolved` unit is
available; the resolved-enabled three-node baseline is never modified merely
to force that branch.

## Deferred

NET-03.1 does not implement HAProxy, global DNS replacement, manual
`resolv.conf` management, arbitrary resolver options, custom health ordering,
or UI work.
