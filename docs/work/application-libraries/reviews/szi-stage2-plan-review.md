## 3. Findings

### SZI2-P01 — BLOCKING — OPEN

**Обещание «не отзывать доступ при disable» не согласовано со штатным обновлением Vault policy.**

**План:** строки 23–25, 203–210, 246–264.
**Код:**

- `ansible-core/collections/ansible_collections/platform/core/plugins/module_utils/application_vault.py:160` — paths строятся из действующих secret bindings.
- Там же, `:188` — policy формируется заново из получившегося набора paths.
- `services/vault/ansible_collections/platform/vault/roles/application_provider/tasks/instance.yml:50` — существующая owned policy заменяется новым содержимым через PUT.

Поведение подтверждено также по исходной версии `5f614312`, без зависимости от dirty AGP.

**Доказательство и влияние.**

Рассмотрим приложение с двумя accounts: `postgres` и `identity`. После выключения `identity` план требует исключить его credential requirements и Agent bindings, сохранив live объекты и доступ. PostgreSQL остаётся активным, поэтому стандартный Vault instance job продолжает выполняться.

Он сформирует policy только для активных bindings и удалит из неё прежний read-path identity account. KV-документ сохранится, но право чтения будет отозвано. Это противоречит прямо заявленному no-revoke, хотя удаления пользователя или документа не произойдёт.

Просто пропустить весь Vault job нельзя: тогда перестанут применяться изменения остальных активных credentials.

**Наименьшая коррекция.**

В плане явно определить retention для Vault policy при отключении/исчезновении интеграции. При сохранении текущего no-revoke решения использовать уже читаемую owned policy: сохранять ранее выданные управляемые read-paths отключённого подключения и добавлять необходимые активные paths, без запроса отключённых паролей.

Не распространять это автоматически на посторонние policies, произвольные capabilities или все инфраструктурные провайдеры. Ownership guards должны сохраниться. Альтернатива — уточнение владельцем границы no-revoke, если оно относится только к объектам Keycloak; это изменение решения, а не техническая трактовка ревьюера.

**Проверка.**

Native сценарий: два accounts → disable одного → Apply оставшегося → ранее выданный токен по-прежнему читает сохранённый identity KV; отключённый пароль не запрашивается и не меняется. Проверить также удаление записи подключения из desired state и повторный Apply.

### SZI2-P02 — BLOCKING — OPEN

**Для проверки неполного scope маршрутов отсутствует определённое общее правило зависимости.**

**План:** строки 331–355; шаги SZI2-01–03.

**Доказательство.**

План одновременно устанавливает:

1. Nginx получает сведения о потребителях всего проекта через Jinja.
2. Core не знает формат маршрутов СЗИ.
3. При изменении requested route input Core блокирует Apply потребителя без библиотеки nginx.

Однако контракт не определяет, по какой декларации Core узнаёт, что изменение выбранного потребителя требует применения другой библиотеки. Сам факт чтения общего project projection внутри шаблона такую зависимость не выражает.

Без этого реализация должна либо знать nginx/СЗИ, либо анализировать зависимости произвольного Jinja, либо полагаться на ручную QA recipe. Первые два варианта нарушают выбранную архитектуру, последний не обеспечивает заявленную проверку плана.

**Влияние.**

Возможны успешно выполненный consumer-only Apply со старым маршрутом либо появление незаявленного механизма определения зависимостей в Core.

**Наименьшая коррекция.**

Зафиксировать одно простое общее правило до реализации. Например, для текущего этапа консервативно требовать включения предоставляющей библиотеки в Apply при установке/обновлении использующего её потребителя. Основание уже есть в `providedConnectionRef`; вычислять «изменился ли именно route input» тогда не требуется.

Цена такого варианта — дополнительный идемпотентный Apply предоставляющей библиотеки. Он не требует DAG, истории рендеров, второго состояния или продуктового условия.

Если требуется более узкая проверка, сначала описать явную декларацию зависимости входов и её владельца; скрыто выводить её из содержимого шаблона нельзя.

**Проверка.**

Target-free кейсы: consumer выбран отдельно; provider выбран вместе с consumer; изменение endpoint/applicationId; отсутствующий provider в scope. Проверить отсутствие target contact, автоматического расширения scope и условий по имени СЗИ/nginx.

### SZI2-P03 — NON_BLOCKING — OPEN

**Нужно явно связать override административного credential с источником bootstrap.**

**План:** строки 107–109, 140–143.

План позволяет менять credential sources предоставляемого подключения и одновременно требует использовать тот же ref, что bootstrap. Не определено, является ли это общей настройкой либо два источника проверяются на равенство.

**Влияние:** после изменения export credential API hooks могут получить другой пароль, чем установленный bootstrap.

**Наименьшая коррекция:** обозначить один canonical source, используемый обоими потребителями, либо явную проверку их согласованности. Смена source не должна подразумевать незаявленную ротацию admin.

**Проверка:** override/reset source, повторная установка с существующим admin, несовпадающие источники; отсутствие секрета в public projection.

## 4. Обязательная оценка overengineering

**Доказанных блокирующих случаев избыточной архитектуры: 0.**

| Категория | Оценка |
| --- | --- |
| Новые абстракции | Предоставляемое подключение оправдано конкретными внутренним и внешним потребителями. Дублирование URL/паролей в каждом приложении проще локально, но создаёт несколько источников конфигурации. |
| Account callbacks | Обоснованы необходимостью выполнить provisioning после готовности приложения, перед стандартной доставкой credentials. Меньшая альтернатива — обычный пакетный hook, но без указанной связи он не определяет границу provider success → Vault. Использование существующего runner разумно. |
| Дублирующие DTO/контракты | Отдельные KeycloakUser/CRUD DTO, registry операций и второй resolver прямо исключены. N/A: подобный механизм в плане не предложен. |
| Persistence | Retained route catalog нужен для согласованного no-delete. Полная перезапись текущей конфигурацией проще, но нарушает это требование. Нельзя использовать каталог как авторитет для desired state. |
| Преждевременный scope | CRUD бизнес-пользователей, массовое подключение библиотек, admin rotation и DAG исключены. Необоснованного расширения не установлено. |
| Более простые механизмы | Основные шаги используют стандартные Ansible tasks и существующие provider/Vault/endpoint paths. Для SZI2-P02 предложена более простая консервативная проверка scope вместо анализа Jinja или нового графа. |
| Endpoint timing | Ранняя публикация через существующий writer соответствует зависимости потребителя от публичного endpoint. Второй механизм публикации не предлагается. |

SZI2-P02 — недостаток определённости контракта, а не утверждение, что избыточный механизм уже реализован.
