# Сценарии установки из пакетов библиотек

Дата: 2026-11-20. Технический план для ревью и решения владельца. База: `568398e353f013d44846581b9f2f39b3268a60cc`.

[Независимое FULL PLAN ревью](reviews/user-scenarios-plan-review.md): APPROVE_WITH_CHANGES, 0 блокирующих замечаний. Уточнение US-P01 внесено.

## Требование и границы

Оператор включает «Демонстрационный проект» в настройках экземпляра библиотеки. При установке СДКУ вызывает пакетный скрипт создания проекта, ЦСПА заполняет выбранный ресурс новой PostgreSQL БД дампом. Автор библиотеки задаёт подпись и явную ссылку на действие в `library.yml`. Один интерфейс отображает сценарии обеих библиотек; новый пакет того же формата не требует пересборки React.

В первой версии сценарий — переключатель с одним типизированным действием. Сценарий действует при обычной установке выбранной библиотеки. Импорт в существующую БД, удаление уже созданных демоданных, отдельный запуск из редактора, внешние дампы, произвольные команды, цепочки действий и формы с собственными входами выходят за объём работы.

### Исходное состояние

- [Общие параметры библиотеки](library-common-defaults-plan.md) используют defaults пакета и сохраняют override в `applicationLibraryDeployments.<id>.overrides.parameters` в group_vars. Общие параметры могут наследоваться приложениями.
- [СДКУ data-manager](../../../examples/sdku/application-packages/data-manager/1.0.0/application.yml) уже объявляет `create-project`, `post_install`, `execution: once`, `run_on: execution_node` с endpoint и фиксированным аргументом `demo`. Скрипт входит в allowlist **пакета приложения**, а не библиотеки. Сценарий должен привязаться к конкретному слоту, а не к имени пакета.
- [ЦСПА](../../../examples/sdku/library-packages/cspa/1.0.0/roles/library_cspa/defaults/main.yml) объявляет несколько ресурсов PostgreSQL, включая `model` (`cspa_tn_scada`). В примере ниже выбран `model`. До выпуска пакета автор ЦСПА подтверждает фактический ресурс, совместимость дампа со схемой приложения и отсутствие секретов и закрытых данных в полном содержимом.
- Действующие контракты: [пакеты и ресурсы](../../project-contract.md), [Core](../../ansible-core.md), [план и события](../../contracts/execution-planning-and-events.md), [post_install](post-install-scripts-plan.md).

## Пакетный контракт

Примеры показывают новые фрагменты `library.yml`; точные поля ниже входят в новую закрытую версию схемы манифеста с поддержкой `user_scenarios` только для `LibraryPackage`. Текущие версии package и role definitions сохраняют прежнюю семантику. Новое поле можно добавить независимо от наличия `scripts` в самом манифесте библиотеки.

СДКУ:

```yaml
user_scenarios:
  demo_project:
    title: Демонстрационный проект
    description: Создать учебный проект после установки СДКУ
    setting: demo_project_enabled
    action:
      kind: package_script
      slot_ref: data-manager
      script_ref: create-project
```

Core сопоставляет `slot_ref` со слотом рецепта и находит `scripts[id=create-project]` в его точной версии пакета приложения. Если сценарий включён, существующий script resolver получает эту декларацию. Runner использует прежние source, phase, target, argv и secretInputs; абсолютные пути, команды и аргументы в сценарии отсутствуют.

ЦСПА:

```yaml
user_scenarios:
  demo_project:
    title: Демонстрационный проект
    description: Заполнить новую базу модели демонстрационными данными
    setting: demo_project_enabled
    action:
      kind: resource_initialization
      resource_ref: model
      restore_on_create:
        source: assets/demo/cspa.dump
        sha256: "<64 hex символа>"
        format: pg_custom
```

Core сопоставляет `resource_ref` с ID управляемого `postgresql.database` в выбранном экземпляре ЦСПА, используя его существующий binding. Проверяет и добавляет `restore_on_create` в производную спецификацию ресурса до формирования provider jobs. Используются действующий контракт restore и allowlist пакета библиотеки. Запись resolved restore обратно в group_vars запрещена.

### Проверки декларации и выбора

- Ограничить число сценариев и размеры строк действующими лимитами метаданных пакетов или меньшими явными пределами схемы. ID, setting, ссылки и текст проверяются при импорте; текст рисуется как обычный текст. Неизвестный тип действия, лишнее поле и неполная ссылка отклоняются.
- В пределах библиотеки ключи setting, ссылки на пару slot/script и цели restore уникальны. Setting — зарезервированный ключ для сценария; конфликт с одноимённым обычным параметром, включая пакетные defaults, блокирует валидацию. Действия всегда разрешаются внутри текущего экземпляра библиотеки. Выбранные сценарии двух экземпляров независимы.
- Неявное значение — `false`. Допустимы только YAML boolean в библиотечном override. Сценарный ключ не передаётся дальше в параметры приложений, шаблоны или argv: Core извлекает его из библиотечного слоя до наследования. Слотовые и хостовые переопределения этого ключа не управляют сценарием.
- Для скрипта первая версия допускает только `post_install` и `execution: once`. Один и тот же package script в другом слоте обрабатывается по декларации этого слота. В паре slot/script под управлением сценария декларация исполняется только при `true` и через обычный resolver ровно один раз по его правилам, без добавления копии в очередь. Включённый сценарий с недоступным слотом, отсутствующим обязательным подключением, отсутствующим endpoint или неразрешимым placement блокирует план вместо молчаливого пропуска. Выключенный сценарий не добавляет собственных runtime inputs и требований readiness. Требования остальных выбранных действий сохраняются.
- Статические ссылки и файлы проверяются также для выключенного сценария. Для restore переиспользовать проверку пути, allowlist и digest; размер и digest проверяются через имеющийся файловый индекс пакета либо один раз на уникальный артефакт за resolve. Включённый сценарий требует однозначного managed PostgreSQL ресурса и разрешённого binding. Если у цели уже есть собственный `restore_on_create`, блокировать конфликт, не определять приоритет поверх него.
- При нарушении выдавать структурированные findings с ID экземпляра библиотеки, ID сценария и полем. Не передавать секреты, содержимое дампа или сырые команды в UI и события.

## Сохранение и интерфейс

В group_vars сохраняется существующий override экземпляра библиотеки. Снятие явного override возвращает пакетное поведение `false`. Полное описание сценария остаётся в точной версии пакета.

```yaml
platform_desired_state:
  applicationLibraryDeployments:
    sdku-main:
      libraryRef: sdku@<новая-версия>
      overrides:
        parameters:
          demo_project_enabled: true
```

Сверка с [дизайном](../../design/ui-design-01.md), [макетом](../../design/ui-design-01-mockups.html) и [планом редактора](milestones/c/c-technical-plan.md): настройка размещается на уровне библиотеки в «Общих параметрах». Макет показывает библиотечный редактор и отдельную «Установку», но специализированного переключателя пока нет. Уточнение дизайна — переключатель и подсказка в существующей вкладке с отметкой наследования. Установка остаётся на существующей странице с теми же действиями. Описание для ЦСПА прямо говорит, что уже созданная база не будет перезаписана.

Расширить существующий структурированный read model библиотечного редактора метаданными `setting/title/description/default` из валидированного package/editor view; использовать текущие draft overrides для редактируемого значения. На выбранной ветке первичный вход во вкладку «Приложения» требует успешной Core-проекции. После допуска сценарий можно настроить до Project Verify: чтение декларативных метаданных и Save выполняются локально через текущий package reader и DTO редактора. Локальная структурная проверка допускает новый формат, разрешение ссылок и условий выполнения остаётся в Core. React выводит общий boolean control и исключает тот же ключ из общего редактора произвольных параметров. При отсутствии или несовместимости метаданных устаревшее управление не отображается.

Путь через существующие edit session → Review → Save, включая reset и reopen. Review показывает разницу значения. Save остаётся локальной транзакцией с действующими guard/rollback, обновляет ревизию и инвалидирует план. Optional Project Verify показывает результат проверки сохранённой ревизии без контакта с целями и без выполнения сценариев.

## Планирование и исполнение

1. Использовать одну функцию разрешения сценариев на канонически разрешённом экземпляре библиотеки после построения слотов/ресурсов и перед существующими provider/script jobs. Результат используется процедурой Validate/Plan и native Apply, без отдельного resolver в Go или React. Не запускать дополнительный ansible-playbook для сценариев.
2. Fresh BuildDeploymentPlan связывает сохранённую ревизию, версии пакетов, их digest, выбранные сценарии, разрешённые цели и существующие действия с текущим runtime и scope. По решению владельца «Установка → План» показывает обычные действия библиотеки без сведений о сценариях. Название сценария доступно в настройках библиотеки. Выбор пропущенной библиотеки остаётся в проекте.
3. На Start сохранить существующую проверку ревизии, runtime, scope и свежего разрешения против утверждённого плана. Смена сценария, источника дампа, скрипта, пакета или цели делает прежнее одобрение неприменимым. Новое поведение без соответствующей поддержки schema/protocol отклоняется до запуска. Ввести версию snapshot/editor projection и plan/manifest только там, где меняется закрытый wire-контракт. Не переводить старые пакеты на новую версию автоматически. Проверить совместимость старого UI/backend и новых пакетов на admission, чтобы они не приняли сценарий как обычный игнорируемый параметр.
4. ЦСПА: PostgreSQL provider до запуска потребителей использует существующий `restore_on_create`, выбор primary, проверку ownership и digest, защищённый staging и cleanup. Новая БД получает дамп. Собственная ранее созданная БД сохраняется. Чужая или не помеченная после неудачи БД блокирует продолжение с диагностикой. Provider не повторяет restore автоматически и не удаляет БД.
5. СДКУ: `create-project` выполняется на существующем этапе post_install после успеха установки. Сохранить разрешение endpoint, учётную запись и текущий runner. Проверить, что скрипт однозначно находит проект и повтор/повтор после ошибки не порождает дубликаты. Если текущее поведение этого не обеспечивает, исправить в версии пакета до публикации. При сбое сценария run получает ошибку по действующему контракту, повтор разрешается через новый план. Выключение сценария после установки не удаляет проект.
6. Использовать имеющиеся context, events и terminal result. Для ЦСПА отличать успешное восстановление от пропуска уже созданной БД по результату provider. Если текущие события не дают однозначного ответа, добавить безопасный outcome в этот же путь. Для СДКУ использовать `changed` и отказ существующего runner. Отказ/отмена предыдущей операции не запускает post_install.

## Обновление пакетов и реализация

1. Core: расширить пакетную схему и admission, типизированную проекцию и один проход разрешения. Перепроверить самостоятельные Ansible entrypoints, выбранный scope, восстановление и разрешение post_install по точной версии слота. Описать правила трассировки в каноническом контракте и решение о пакетных сценариях в ADR.
2. Backend/UI: привязать дескриптор к проверяемой версии пакета, добавить проекцию и переключатель, сохранить существующий writer и планирование. Обновить руководство UI и макет. Проверить сброс значения, одновременное редактирование и замену пакета с удалённым/переименованным setting. Не удалять старый override молча: сообщить конфликт и потребовать осознанного reset или замены до плана.
3. Выпустить новые версии СДКУ и ЦСПА после подтверждения их активных slots/resources и тестового дампа. Старый СДКУ запускает `create-project` как раньше. При явном переходе на новую версию UI/описание пакета сообщают, что демо теперь включается отдельно. Новый СДКУ использует декларацию слота один раз; проверить, что на общем контуре другая декларация `create-project` не создаёт тот же объект. Удаление демо из старой БД не входит в миграцию.
4. Перед bundle-dependent QA выполнить [процедуру bundle](../../agent-procedures/runtime-bundle.md), перед Core/Wails проверками — [процедуру QA](../../agent-procedures/qa.md). Публикация verified bundle, запуск на тестовых целях и выпуск пакетов следуют только после разрешения соответствующих работ и прохождения нужных проверок.

## Приёмка

| Уровень | Обязательные доказательства |
| --- | --- |
| Core и schema на RED OS | Старый пакет без изменений. Включение, выключение, два экземпляра и два слота с одним пакетом. Ошибки ссылок, конфликт restore, тип override, неверный формат/путь/digest, несовместимый runtime. Core Verify без target contact, Start со сменённым выбором/артефактом отклонён. |
| Native Apply и события | СДКУ без включения не вызывает gated script и не запрашивает секрет, нужный только ему. Секрет и readiness, нужные обычной установке, остаются обязательными. С включением ровно один вызов по slot context, повтор без дубликатов, skip/сбой до post_install. ЦСПА: restore в новую БД и фактическая проверка контрольных данных, повтор без восстановления, чужая/частичная БД блокирует, защищённые временные файлы очищены. |
| Реальный React → Wails → Core | Импорт пакета, отображение до Verify, Review/Save и reopen обоих экземпляров, reset, Verify и новый план, Approve → Start в изолированном контуре. Записать revision/plan/run IDs, terminal outcomes, фактический результат каждой библиотеки и повтор. Проверить интерфейс отдельно по макету. Harness и mocks дополняют эту проверку. Недоступный bridge блокирует приёмку. |
| Производительность | До merge измерить baseline/changed на одном RED OS узле и одном проекте, хостах, scope и входах. Отдельно сравнить прежние пакеты и новые пакеты с выключенными сценариями по одному fixture для обеих ревизий, а активные сценарии сравнить с эквивалентными legacy явными действиями. Для каждого затронутого этапа записать число resolver/runner вызовов, хеширований, subprocess и Ansible task counts, повторные timings при одинаковом состоянии БД. Регрессии: ноль новых playbook invocations и новых действий при выключении, одно разрешение на библиотеку за проход, не более одной проверки digest на уникальный asset за resolve, один вызов gated script по slot context. Устранить повторную работу либо согласовать измеренную стоимость. |

Изменение публичного контракта требует независимого FULL DIFF. Свидетельства идут в отдельный QA-журнал. Текущий статус фиксируется в CURRENT_STATE после одобрения и по мере фактического прохождения этапов.
