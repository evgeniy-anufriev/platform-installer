# План независимой публикации HTTPS и TCP для приложения

Один экземпляр приложения может публиковать HTTPS, TCP, оба маршрута или ни одного. На первом этапе поддерживаем по одному маршруту каждого типа, с общей группой endpoint и отдельным портом приложения для каждого маршрута. TCP передаёт поток без TLS-терминации на HAProxy. Выбор сертификата TCP-приложения и протокол поверх TCP остаются за приложением.

## 1. Настройки проекта и совместимость

Пример в настройках приложения, оба маршрута включены:

```yaml
endpoints:
  https:
    enabled: true
    listener: web
    protocol: https
  tcp:
    enabled: true
    listener: data
    public_port: 9000
```

- `enabled` относится к своему маршруту. `https.enabled: false` вместе с `tcp.enabled: true` означает только TCP. Обратная комбинация означает только HTTPS. Выключенному маршруту достаточно `enabled: false`. Core проверяет типы, допустимые поля и диапазон публичного порта. Для включённого маршрута нужны объявленный `listener` и его `ports.<listener>.published` в каждом размещении.
- При отсутствии `endpoints.https` Core использует эффективный старый `endpoint` как HTTPS-маршрут. При наличии `endpoints.https` он задаёт маршрут целиком, в том числе явно выключает унаследованный старый HTTPS. TCP появляется только при явном включении `endpoints.tcp`. Добавление одного TCP-блока к старому проекту сохраняет старый HTTPS. Удаление нового HTTPS-блока возвращает унаследованную настройку, поэтому команда «Выключить» записывает `enabled: false` явно.
- Оба маршрута используют существующую эффективную группу приложения. Источники и приоритет группы остаются прежними, включая `endpoint.endpoint_group` и действующую привязку библиотеки. В `endpoints` указываются только параметры маршрутов. Нормализовать маршруты в одном месте Core после действующего Ansible-разрешения. Save сохраняет авторские поля, включая старые Jinja-выражения, и допускает одновременное наличие старого `endpoint` и нового `endpoints` по этим правилам. Фоновая миграция не требуется.
- Для старого `endpoint` сохранить FQDN, URL, настройки backend и probe, имя HAProxy backend и фрагмента. `https.protocol` по-прежнему означает транспорт до приложения, а снаружи используется действующий HTTPS frontend. Скрипты и подключения, запрашивающие существующий HTTPS endpoint, получают прежний HTTPS URL. При TCP-only Core сообщает о недостающем HTTPS, если выбранный шаг требует именно его. Сам TCP-only допустим.

## 2. Разрешение маршрутов и планирование

Сохранить один логический источник на `instanceId`. Если включён хотя бы один маршрут, Core вычисляет общий FQDN и провайдеров по существующей политике группы. Для каждого включённого маршрута он собирает свой список адресов и опубликованных портов размещений. Публичный порт TCP и общие настройки маршрута должны совпадать между размещениями. В проекции TCP-only есть DNS-имя и TCP-порт. Публичный HTTPS URL и его проверка относятся к маршруту HTTPS. Сохранить действующие правила PKI приложения, прямого HTTPS к размещению и TLS общего frontend HAProxy.

Перед фильтрацией выбранных источников проверить полный набор известных привязок TCP по каждому провайдеру и хосту. Сравнить с эффективными портами public/stats, TCP-маршрутами других приложений, в том числе из других групп, и известными локальными портами совместно размещённых компонентов. Проверить уникальность имён генерируемых proxy. Подключить расчёт к существующему Project Verify без обращения к целевым хостам и к BuildDeploymentPlan. В согласуемом плане и его отпечатке отразить желаемые маршруты, параметры и цели. При выключении обоих маршрутов Review и план показывают, что обычный Apply пропустит публикацию, а ранее активный фрагмент снимается отдельным полным HAProxy reconcile. Start сохраняет действующую проверку актуальности сохранённой ревизии и плана.

Предлагаемая привязка для первой версии — `*:public_port` по аналогии с общим HTTPS frontend. Это открывает TCP-порт на всех адресах выбранного HAProxy-хоста. Перед реализацией владелец подтверждает эту область доступа. Если требуется только VIP, сначала проверить привязку сокета на резервном узле и переключение VIP. Политику доступа и firewall отразить в плане, сохраняя действующий порядок их изменения.

## 3. Публикация и снятие маршрутов

Переиспользовать один управляемый фрагмент на источник и группу. Фрагмент содержит обычный HTTP backend для HTTPS-публикации, отдельный `listen` в `mode tcp` либо обе секции. Имя TCP proxy должно быть стабильным и исключать выбор секции через динамическое HTTP-правило `use_backend`. TCP-only сохраняет тот же FQDN в DNS и не генерирует HTTP backend для приложения.

Использовать существующий пакетный prepare/activate с одним полным кандидатом на хост и действующим порядком проверки и reload. Выключение одного маршрута перезаписывает тот же фрагмент, удаляя только его секцию. Смена TCP-порта закрывает старый bind после reload. При совпадении графа повторный Apply не запрашивает reload. DNS публикуется один раз на источник.

Выключение одного маршрута при действующем втором обновляет фрагмент HAProxy. По решению владельца по TCP-P04 при выключении последнего маршрута сохраняется существующее поведение. Обычный Apply исключает приложение из списка источников, пропускает публикацию этого приложения и оставляет ранее активный фрагмент. Снятие выполняется отдельным [полным HAProxy reconcile](../../../services/haproxy/playbooks/reconcile.yml) на HAProxy-хостах, где была публикация. Reconcile строит полный кандидат из актуальных настроек и использует существующие проверки владения и архивацию устаревших управляемых фрагментов. По TCP-P05 DNS-запись сохраняется и после обычного Apply, и после HAProxy reconcile. Удаление экземпляра и перенос группы выходят за рамки этого изменения.

`haproxy -c` валидирует конфигурацию. Проверку фактического bind и доступности выполнить после reload. Для занятия порта сторонним процессом и сбоев активации сохранить действующий порядок диагностики и восстановления. Многоузловая публикация сохраняет существующие границы отката.

## 4. Проверка трафика и интерфейс

- В существующем пакетном этапе проверять каждый включённый маршрут. Для HTTPS сохранить TLS и HTTP-проверки. Для TCP проверить соединение с целевыми портами приложений с HAProxy и доступность публичного TCP-порта со стороны клиента. TCP-соединение показывает доступность транспорта. Приёмочный тест дополнительно подтверждает обмен данными через HAProxy с тестовым приложением. Для TCP-only не выполнять запрос к порту 443 от имени этого приложения.
- После standalone Core обновить существующий раздел Endpoint экрана приложения. Два независимых переключателя HTTPS и TCP, выбор listener для каждого маршрута и публичный порт TCP. Текущая настройка группы сохраняется. В Review и плане показать изменения маршрутов и адреса из Core. UI и Go переиспользуют штатный writer, а правила маршрутизации остаются в Core. Сверить затронутые поля с текущими макетами до реализации и при приёмке.

## 5. Приёмка и стоимость

1. На настроенной RED OS проверить четыре комбинации флагов и старый проект без `endpoints`. Отдельно проверить старый HTTPS плюс новый TCP, явное отключение унаследованного HTTPS, TCP-only с HTTPS-зависимостью выбранного шага, разные порты на размещениях, занятый порт, общий HAProxy узел у разных endpoint-групп.
2. Проверить переходы HTTPS → оба → TCP → оба выключены и обратное включение HTTPS, смену TCP-порта, повторный Apply, целостность соседних и сторонних фрагментов. После выключения последнего маршрута подтвердить, что обычный Apply оставляет ранее активный фрагмент, а отдельный полный HAProxy reconcile архивирует его и закрывает маршрут. После обеих операций проверить сохранение DNS-записи приложения. Для HA-топологии подтвердить TCP-трафик после переключения VIP, если он используется.
3. Через реальные React/Wails выполнить Save, повторное открытие, Verify, Plan, Approve и Start на тестовом проекте. Зафиксировать сохранённую ревизию, run ID, итоговый статус, адреса и факт обмена данными. До изменения runtime пройти действующие процедуры bundle и QA.
4. Сравнить до/после на том же проекте и Execution Node, с теми же хостами и операциями. Зафиксировать повторные замеры времени, число запусков resolver, задач Ansible и циклов подготовки/reload. Закрепить регрессией один расчёт полного набора привязок на проход и один цикл подготовки на провайдер-хост. Для старого проекта проверить отсутствие дополнительных сетевых проверок.

Затронутые контракты — [портативный проект](../../project-contract.md), [интеграция приложений A6](implementation-plan.md#a6-endpoints-через-существующие-haproxydns-hooks), [дизайн UI](../../design/ui-design-01.md). Реализация начинается после согласования контракта и области bind. Порядок снятия последней публикации согласован по TCP-P04.

## Решение владельца по FULL DIFF

Владелец снял TCP-D01–TCP-D04 как блокеры этой доработки. Дополнительные требования ревью по провайдерам, согласованности размещений, доказательству поколения HAProxy после reload и наследованию в редакторе не входят в обязательный объём реализации. Для этих замечаний ревью привело возможные сценарии по исходникам. Воспроизведённые сбои в ходе ревью не зафиксированы.

Исходный вердикт FULL DIFF `BLOCK` относится к проверенному набору изменений с SHA-256 `9343e8b0e12a9dc10d18b4c07b9d22a65768c0a0db26fb1e566f4c3c7f1b2646`. Решение владельца снимает эти четыре блокера без изменения вердикта рецензента. Приёмка по разделу 5 остаётся обязательной.
