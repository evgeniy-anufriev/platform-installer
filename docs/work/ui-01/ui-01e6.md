## Windows Wails acceptance

The production executable built with `wails build -nopackage -clean` was
started with the existing trusted READY RED OS binding and verified immutable
bundle. The real Wails/React flow created an isolated metadata-only project
through the Create Project modal using its manually entered full project path.
It contained only `project.yml`; its SHA-256 stayed
`cfcf7a8abdff4d4b4e8b8431549059a24aa9e52b62676689f249ce259cc615df`
before cleanup.

The project had zero servers. `192.168.56.101` appeared only as the explicit,
runtime-only startup Execution Node binding; it was never persisted to
`project.yml`, inventory, host variables or a draft.

The UI proved:

- local state `Сохранено` / `Не проверено` for a metadata-only project;
- Servers availability before topology/service editors;
- the fixed lower Execution Node panel and `EXPLICIT` selection origin;
- read-only `Проверить узел` returns `READY`;
- the global badge changes to `Execution Node: READY` and Installation becomes
  available;
- Installation retains the fresh authoritative `DeploymentPlan` prerequisite
  and locates Execution Node preparation only on Servers.

The node reported RED OS 8.0.3/x86_64, elevation available, immutable release
`qa-ui-01e2-20260914-02`, bundle
`sha256:dcdd5ea9bec9cc6bf842ae3a15f5f7ff9e71f144fadafc2ac8be79b37cd49ad8`,
Core `0.1.0`, protocol `v1alpha1` and capabilities present. It was already
READY, so E6 did not invoke mutating Prepare, activate a release, install a
service or contact target nodes.

The existing opt-in Wails-bound remote CRUD acceptance passed against the same
binding in 0.35 s and proved local first-save/CRUD plus authoritative,
