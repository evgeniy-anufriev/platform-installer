# SI08 — независимость запуска от доставки защищённых результатов

Document scope: the original milestone contract/design. Historical status, review
and QA checkpoints are collected separately; current status and authorization
are recorded only in [CURRENT_STATE](../../../CURRENT_STATE.md).

Recorded status and review scope: [historical checkpoint](evidence/documentation-checkpoints-20261012.md#si08-output-run-delivery-decoupling-checkpoint-001).



## Решение владельца

Execution Node отвечает за создание и долговременное сохранение защищённого
пакета своего run. После завершения работы producer сохранённый пакет доступен
для получения; успех, ошибка или отсутствие доставки на рабочую станцию не
меняют итог run и не ограничивают запуск следующего run. Старый пакет `READY`
или `ACKED_CLEANUP_PENDING` не является причиной `OUTPUT_BUSY` при подготовке
нового пакета того же проекта и размещения.

Installer после завершения run автоматически **пытается** получить и локально
зашифровать его выходные файлы. Это действие Go/UI: Execution Node предоставляет
пакет, но не инициирует соединение с рабочей станцией и не ждёт результата
доставки. Ошибка автоматической доставки отображается отдельным статусом;
повторное получение возможно по явному действию. Обычная доставка не посылает
Execution Node подтверждение как условие готовности run или нового запуска.
Автоматическая доставка не удаляет удалённый пакет. Его удаление — отдельная
явная операция, не входящая в этот план. Существующий `Acknowledge` не должен
вызываться автоматическим путём и не должен использоваться как допуск Start;
пока отдельная очистка не реализована, он сохраняется для совместимости, но
не становится частью нового нормального сценария.

Для следующего запуска Vault пользователь при необходимости выбирает ранее
сохранённые зашифрованные файлы в окне «Секреты» сервиса. Installer не ищет их
автоматически и не подставляет в runtime-входы сервиса.

## Узкие изменения

1. В `execution_secret_output.prepare_package_identity` сохранить существующую
   неизменяемую привязку `sourceRunId → packageId/generation`, эксклюзивное
   создание, lock для пары project/deployment и монотонное поколение. Выделять
   новому run новый пакет независимо от `READY`/`ACKED_CLEANUP_PENDING`
   **предыдущего** пакета. Подготовка нового пакета не должна брать lock старого
   пакета, который может удерживаться `Fetch` или прежней очисткой. Для подсчёта
   поколений использовать существующие неизменяемые reservation-записи с
   проверкой структуры и совпадения идентичности. Неизвестная или повреждённая
   reservation, конфликт поколений и незавершённая частичная запись без
   доказанного безопасного состояния по-прежнему дают явную ошибку
   восстановления; не удалять и не исправлять их догадкой. Повторная попытка
   **того же** run остаётся привязанной к прежнему packageId. Существующий
   запрет одновременно активных mutating runs для проекта сохраняется.
2. На рабочей станции новые зашифрованные комплекты публиковать без замены в
   `secrets/<deploymentId>/<packageId>/`. Использовать нынешний временный
   `.platform-export-*` и атомарную публикацию каталога, квитанцию `complete`,
   проверку файлов после записи и защиту от подмены пути. Существующий
   `secrets/<deploymentId>/{admin-token.age,unseal-shares.age,complete}` —
   прежний опубликованный комплект; оставить его на месте и поддерживать чтение
   при явном выборе именно этого пакета. Каталоги `.platform-export-*` без
   успешной публикации не считаются доставленными поколениями, не удаляются
   автоматически и не заменяют квитанцию конечного каталога.
3. Получение пакета всегда адресовать точными `projectId`, `deploymentId`,
   `packageId`, `sourceRunId`, `generation`, `runtimeDigest` из доверенного
   списка/квитанции. Повтор после перезапуска проверяет `complete` и
   зашифрованные файлы **точного packageId**, а не ищет произвольный комплект
   по имени размещения или текущему runtime digest. Старый плоский каталог
   проверяется только для совпадающего packageId; новый пакет его не
   перезаписывает. Повторная доставка того же пакета идемпотентна.
4. Обработчик завершения run автоматически пытается доставить пакеты,
   принадлежащие завершившемуся run; исторические пакеты остаются в списке и
   могут быть получены явно. Ошибка одного пакета не меняет терминальный
   статус run и не препятствует следующему Start. UI показывает раздельно итог
   установки и итог доставки, а рядом с пакетом — исходный run и поколение.
   Устаревший текст о том, что прежний `READY` останавливает новый запуск,
   убрать из интерфейса и макета при реализации.

## Границы и совместимость

- Без изменения Vault-роли, обычного standalone Ansible, публичных схем
  Start/Result/Events, канонического проекта и правил Ansible.
- Без хранения открытых секретов в проекте, UI, событиях или диагностике.
- Существующие удалённые пакеты и опубликованные локальные файлы сохраняются.
  Пакеты на Execution Node остаются до отдельной явной очистки; обычная
  run-history cleanup не удаляет их.
- `SecretOutputDelivery/v1alpha1` и `Acknowledge` не переопределяются молча:
  вызов ACK исключается из нормального автоматического сценария. Если изменение
  версии контракта окажется обязательным, это отдельное решение до кодирования.
- Верхняя граница существующего списка пакетов (4096) остаётся ограничением;
  накопление пакетов не решается автоматическим удалением в этом этапе.

## Проверка результата

- Два последовательных run одного размещения: первый оставляет `READY`, второй
  стартует и получает другой packageId и следующий generation; оба пакета
  остаются доступны. Lock старого пакета при Fetch не блокирует подготовку
  нового. Повтор Start того же run не создаёт третье поколение.
- Незавершённая reservation, частичная пара файлов, повреждённая metadata,
  совпадение generation и сбой во время записи дают безопасный исход без
  удаления последнего экземпляра секрета.
- Два локальных комплекта сохраняются в разных каталогах; любой порядок
  повторного получения, перезапуск Installer, смена runtime digest, старая
  плоская раскладка, коллизия каталога, symlink/reparse и отказ flush не
  приводят к перезаписи или ложной отметке о доставке.
- Завершение run B не доставляет автоматически пакет run A. Неудачная
  автодоставка B оставляет run B с его фактическим терминальным результатом и
  позволяет новый Start; пакет B доступен для ручного повтора.
- Затронутые Python/Core и Go тесты, frontend-тест статусов, проверка
  реального React/Wails обработчика с Go и Execution Node без установки
  сервисов. Никакие результаты тестов этим планом пока не заявлены.

## Источник решения

Владелец подтвердил отдельную ответственность Execution Node и доставки,
сохранение автоматической попытки доставки, новый packageId/generation для
каждого run и локальный путь по packageId. План закрывает замечания первого
FULL PLAN review `SI08-OUTPUT-PLAN-01`–`04` и передаётся на разрешённый
`TARGETED_RECHECK` этих пунктов. Первоначальное ревью было `BLOCK`; это не
считается одобрением реализации.
