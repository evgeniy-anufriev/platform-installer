# План добавления сервиса Chrony

## Пакет и standalone Ansible

- Добавить `services/chrony` с манифестом, схемой настроек, совместимостью, Ansible-коллекцией, playbooks Apply и Verify, примером inventory и инструкцией запуска. Подключить пакет к существующей генерации каталога и сборке runtime bundle. Зарегистрировать `chrony` в существующем списке разрешённых сервисов execution controller с путями `services/chrony/playbooks/{apply,verify}.yml`. Использовать действующую политику источников RPM.
- Объявить один режим развёртывания Chrony с ролями `server` и `client` и явным размещением. Роль `server` раздаёт время по собственным системным часам через локальный источник, например `local stratum 10`, и обслуживает разрешённые сети клиентов по UDP/123. Эффективная конфигурация сервера исключает вышестоящие источники, включая полученные через DHCP. Роль `client` использует заданный FQDN или IP NTP-сервера и отключает входящий NTP.
- Использовать обычные переменные Ansible и одну реализацию ролей для Installer и standalone. Standalone Apply выполняет серверную роль перед клиентской. Проверять конфигурацию перед заменой и перезапускать службу при изменении. До изменений сообщать о конфликте с чужой конфигурацией, противоположной управляемой ролью или другой службой времени. Допускать повторный Apply и обновление настроек той же роли. По умолчанию клиент может корректировать часы скачком при смещении больше одной секунды в первые три обновления после запуска Chrony.

## Топология и Сервисы

- В «Топологии» оператор добавляет экземпляр Chrony и назначает его участникам роли `server` и `client`. В «Сервисах» в настройках участника клиентской роли задаёт адрес NTP-сервера, а для серверной роли — разрешённые сети (CIDR). Клиент может использовать адрес сервера из того же экземпляра или внешний адрес. Поддержать размещение только клиентов для сценария с внешним NTP-сервером.
- Использовать существующий редактор строковых настроек участника. Разрешённые сети задаются строкой с CIDR через запятую. Указать в подсказках область применения каждого поля. Сохранение использует штатный Review/Save. Использовать существующую структурную проверку схемы, без отдельного набора проектных проверок Chrony в Core.

## Один план установки

- Добавить обычную запись `chrony` в `serviceExecutionPriorities` в `config/application.yml`. Она задаёт место Chrony среди сервисов.
- В манифесте задать `minMembers: 1`, `distinctHosts: true` и `x-memberListVariable: platform_chrony_instances` для Apply и Verify. Использовать этот же список участников в standalone inventory. Перед группировкой загрузить `platform.core.runtime_role_variables`, когда передана конфигурация исполнения. До изменений Ansible проверяет, что каждому хосту назначена ровно одна роль и заданы её обязательные настройки.
- В `services/chrony/playbooks/apply.yml` использовать последовательность из [Apply playbook PostgreSQL](../../../services/postgresql/playbooks/apply.yml), где монитор устанавливается перед узлами данных. Сгруппировать хосты экземпляра по назначенным ролям, выполнить серверный play, затем клиентский. Ошибка серверного play останавливает Apply до запуска клиентского. Для размещения только клиентов серверный play пропускается.
- Один утверждённый план содержит один Apply экземпляра Chrony с обеими ролями, затем Verify. Порядок ролей задаётся в Ansible playbook и действует одинаково в Installer и standalone.

## Verify и приёмка

- Для клиента Verify проверяет состояние службы и фактическую синхронизацию с заданным источником с ограниченным ожиданием. Для сервера Verify проверяет только состояние службы.
- На изолированных хостах RED OS выполнить standalone Apply и Verify обеих ролей. Проверить синхронизацию клиента с локальным сервером без вышестоящего источника, ограниченное ожидание при недоступности источника и повторный Apply без изменений.
- Опубликовать проверенный runtime bundle штатным способом. Через реальные React/Wails-обработчики разместить обе роли в одном экземпляре, сохранить адрес, открыть проект повторно, выполнить Project Verify и провести обе роли через один утверждённый план. Зафиксировать сохранённую ревизию, ID запуска, порядок серверного и клиентского plays и результат Verify. Дополнительно проверить размещение только клиентов и остановку до клиентского play при ошибке установки сервера.
